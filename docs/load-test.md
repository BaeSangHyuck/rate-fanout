# 부하 테스트와 대응

k6로 단계적으로 부하를 올리며 두 API의 한계와 원인을 찾고, 고친 뒤 같은 조건으로 다시 측정했습니다. 아래 수치는 모두 GitHub Actions에서 실제로 돌린 결과입니다. 결과 파일은 `loadtest` 워크플로 실행의 `loadtest-results` 아티팩트에 남아 있습니다.

## 측정 환경과 방법

| 항목 | 값 |
|---|---|
| 실행 위치 | GitHub Actions `ubuntu-latest` 러너 1대 (4 vCPU) |
| 구성 | 앱(JVM 21, Hikari 커넥션 10개) + Postgres 17 + Redis 7.4 + k6가 모두 같은 러너에서 실행 |
| 부하 방식 | `ramping-arrival-rate`: 초당 요청 수를 고정해서 보낸다. 20초 동안 목표의 1/4까지, 다음 20초 동안 목표치까지 올리고, 20초 유지 |
| 서버 지표 | 1초마다 `/actuator/prometheus`를 수집(Hikari 사용 중·대기 커넥션, CPU, 스레드). 최고 부하 구간에서는 `jcmd Thread.print`로 스레드 덤프 |
| 스크립트 | `loadtest/coupon-issue.js`, `loadtest/quote.js`, `.github/workflows/loadtest.yml` |

앱과 부하 발생기가 같은 머신에 있으므로 절대값보다 **같은 조건에서의 방식 간 비교**로 읽어야 합니다. 쿠폰 테스트는 같은 설정으로 8번 돌렸고 결과가 재현됐습니다. 범위는 표에 함께 적었습니다.

## 1. 선착순 쿠폰 발급

사용자 한 명의 클릭이 HTTP 요청 하나(`POST /api/coupons/{id}/issue`)가 되도록 했습니다.
- 쿠폰 수량 5,000개, 사용자 20,000명 중 무작위로 요청합니다. 같은 사용자의 재요청도 섞입니다.
- 발급 처리 시간은 5ms입니다.
- 클라이언트 타임아웃은 10초입니다.

### 결과 (목표 초당 400건, 총 14,500건)

| 방식 | 처리량 | p50 | p95 | 실패(10초 초과) | 보내지도 못한 요청 | Hikari 사용 중 / 대기 |
|---|---|---|---|---|---|---|
| 비관적 락 | 141–144건/s에서 막힘 | 5.4–6.1초 | 10초(타임아웃) | 23.0–32.2% | 4,312–4,593건 | 10 / 54 |
| 조건부 UPDATE | 242건/s (목표 전부 처리) | 6ms | 7ms | 0% | 0 | 최대 3 / 0 |
| Redis 게이트 | 242건/s (목표 전부 처리) | 1ms | 7ms | 0% | 0 | 최대 3 / 0 |

목표를 초당 1,500건으로 올린 결과입니다(총 약 53,000건).

| 방식 | 처리량 | p50 | p95 | p99 | 실패 |
|---|---|---|---|---|---|
| 비관적 락 | 169건/s | 10초 | 10초 | 10초 | 51.0%. 테스트 시간 안에 5,000개 중 4,050개만 발급 |
| 조건부 UPDATE | 883건/s | 6ms | 8ms | 13ms | 0% |
| Redis 게이트 | 883건/s | 1ms | 7ms | 8ms | 0% |

모든 실행에서 부하가 끝난 뒤 DB의 발급 건수를 확인했습니다. 수량 5,000을 넘긴 적은 없습니다.

### 원인: 비관적 락이 커넥션을 쥔 채로 줄을 선다

- 비관적 락 구간에서 Hikari는 사용 중 10, 대기 54에서 멈춰 있었습니다. 54는 코루틴 IO 디스패처의 스레드 64개에서 커넥션 10개를 뺀 수입니다.
- 쿠폰 행 하나의 락을 기다리는 동안 요청이 DB 커넥션을 놓지 않습니다. 그래서 커넥션 10개가 "락 대기"에 묶이고, 나머지 요청은 커넥션을 기다리고, 그 뒤 요청은 스레드를 기다립니다.
- CPU는 최대 37~53%로 여유가 있었습니다. 즉 계산이 아니라 **락 하나에서 직렬화되는 것**이 한계입니다. 처리량은 "락을 쥐는 시간"의 역수인 초당 140~170건 근처에서 더 오르지 않습니다.
- 커넥션 풀은 다른 API와 같이 쓰는 자원입니다. 그래서 이 상태에서는 쿠폰과 상관없는 DB API까지 커넥션을 못 받습니다.

### 대응

**적용한 것**
- **조건부 UPDATE**(`UPDATE … SET remaining = remaining - 1 WHERE remaining > 0`)
  - 확인과 차감을 한 문장으로 처리해서 행 락을 그 문장 동안만 잡습니다. 처리 시간(5ms)은 락 밖에서 씁니다.
  - 초당 883건에서도 p95 8ms였습니다.
- **Redis 게이트**(Lua 스크립트로 중복 확인·수량 확인·차감을 원자적으로 처리)
  - 통과한 5,000건만 DB까지 가고, 나머지 약 48,000건은 DB 커넥션을 잡지 않고 바로 돌아갑니다.
  - 이 부하에서 p95는 조건부 UPDATE와 비슷했고, 차이는 p50(1ms vs 6ms)과 p99(8ms vs 13ms)에서 났습니다.
  - 조건부 UPDATE도 품절 뒤에는 "0행 업데이트"라 가볍기 때문에, 이 규모에서는 둘 다 충분합니다. Redis 게이트는 DB가 다른 트래픽과 같이 쓰일 때, 또는 수량이 커서 DB 쓰기 자체가 많을 때 의미가 커집니다.

**더 할 수 있는 것** (구현하지 않음)
- 비관적 락을 꼭 써야 하는 곳이라면:
  - 락 대기 상한(`jakarta.persistence.lock.timeout`)을 둬서 오래 기다리는 대신 빨리 실패시킵니다.
  - 해당 기능의 커넥션 풀을 분리해서(벌크헤드) 다른 API로 번지지 않게 합니다.
- 입장 대기열: 처리량 한도를 넘는 요청은 대기열 토큰을 주거나 429로 돌려보내 서버 안에 쌓이지 않게 합니다.
- 핫 로우 분산: 수량을 여러 행(버킷)으로 나눠 락 경합을 나눕니다.

## 2. 대출 조건 병렬 조회 (외부 API fan-out)

`GET /api/quotes` 요청 하나가 서버 안에서 모의 금융사 12곳으로 HTTP 호출을 동시에 보냅니다.
- 기관별 타임아웃은 2초, 에러 시 재시도는 1회입니다.
- 모의 기관은 시나리오 번호로 지연과 에러가 정해집니다. 그래서 부하가 없을 때의 기관별 타임아웃 비율(기준선)이 약 11%로 고정돼 있습니다.
- 부하 때문에 이 비율이 올라가면 그만큼 서버 쪽 병목입니다.

### 결과

| | 평균 처리량 | 기관 타임아웃 비율 | 정상 응답 비율 | 응답 p95 |
|---|---|---|---|---|
| 기준선 (초당 3건) | 3건/s | 11.7% | 87.5% | 2.32초 |
| 목표 60건/s, **수정 전** | 34건/s | **44.6%** | 54.0% | 3.61초 |
| 목표 60건/s, **수정 후** | 34건/s | 11.7% | 87.2% | 2.31초 |
| 목표 120건/s, **수정 전** | 65건/s | 27.9% | **32.2%** (나머지는 즉시 에러) | 3.48초 |
| 목표 120건/s, **수정 후** | 67건/s | 11.2% | 87.7% | 2.33초 |

수정 후에는 초당 120건(평균 67건)까지 기준선과 같은 결과가 나왔습니다.

### 원인을 찾은 과정

1. **CPU·스레드 확인**
   - 부하 중 CPU는 최대 22~52%로 포화되지 않았습니다.
   - 최고 부하 때 스레드 덤프를 보면 Netty 이벤트 루프와 코루틴 워커가 모두 대기 상태였습니다. 서버가 바쁘지 않은데 타임아웃이 늘고 있었습니다.
2. **모의 기관 분리**
   - 모의 기관이 같은 프로세스에 있어서 부하를 같이 받는다는 의심이 있었습니다.
   - 모의 기관을 별도 프로세스로 띄워도 결과가 같았습니다(타임아웃 42.7%). 원인이 아니었습니다.
3. **로컬 재현**
   - 12코어 PC에서 Java로 만든 부하 발생기로 초당 3, 20, 60건을 보냈습니다. 20건까지는 정상이고 60건에서 똑같이 무너졌습니다.
   - 부하 중 응답을 열어 보니, 원래 0.15~0.4초 걸리는 에러 응답이 1.4초 뒤에 왔고 재시도는 0ms 만에 실패했습니다. 모든 호출이 약 1.2초씩 늦게 시작하고 있었습니다.
4. **구간 분리**
   - 같은 부하 중에 모의 기관을 curl로 직접 부르면 0.7초(정상)였고, 헬스 체크는 3ms였습니다. 받는 쪽은 멀쩡했습니다.
   - 늦어지는 곳은 **우리 서버가 기관을 부르는 WebClient의 커넥션 풀**이었습니다.
5. **필요한 크기 계산(리틀의 법칙)**
   - 동시에 필요한 커넥션 = 초당 조회 60건 × 기관 12곳 × 호출당 약 1초 = 약 720~900개입니다.
   - Reactor Netty 기본 풀로는 호출들이 풀 앞에서 기다리다 2초 타임아웃에 걸렸습니다.
   - 처음에 500으로 늘렸을 때는 여전히 모자랐습니다. 대기열(기본 최대 크기의 2배)이 넘치면서 이번에는 즉시 에러로 바뀌었습니다.

로컬(12코어)에서 초당 60건, 풀 크기만 바꿔 비교한 결과입니다.

| 커넥션 풀 | 기관 타임아웃 | 정상 응답 | 응답 p95 |
|---|---|---|---|
| Reactor Netty 기본값 | 39.0% | 54.4% | 3.63초 |
| 500 | 11.3% | 42.6% (대기열 초과로 즉시 에러) | 3.53초 |
| 2000 | 5.2% | 83.5% | 2.31초 |

### 대응

**적용한 것**
- **커넥션 풀 크기를 2000으로**(`app.quote.max-connections`). 필요한 양(약 900)에 여유를 둔 값입니다.
- **풀 지표 노출**(`ConnectionProvider.metrics(true)`): `reactor_netty_connection_provider_*` 지표가 Prometheus에 나옵니다. 처음부터 이 지표가 있었다면 1~4단계 없이 바로 보였을 병목입니다.
- (기존) 기관별 `withTimeout`과 에러 시 재시도, 그리고 실패를 결과로 담는 부분 응답 덕분에, 부하 중에도 5xx는 0건이었습니다. 느려진 기관만 빠졌습니다.

**더 할 수 있는 것** (구현하지 않음)
- 풀 크기만 키우면 부담이 실제 외부 기관으로 넘어갑니다. 실제 기관은 호출 제한이 있으므로 **기관 단위 동시 호출 제한**(전역 Semaphore 또는 Resilience4j Bulkhead)을 둡니다.
- 계속 실패하는 기관은 **서킷 브레이커**로 일정 시간 호출 자체를 건너뜁니다.
- **풀 대기 상한**(`pendingAcquireTimeout`)을 기관 타임아웃보다 짧게 둬서, 풀이 모자랄 때 2초를 다 쓰지 않고 빨리 실패시킵니다.
- 같은 사용자가 짧은 시간에 다시 조회하면 **결과 캐시**(Redis TTL)로 기관 호출을 생략합니다.

## 공통: 운영에서 볼 지표와 기준

| 지표 | 의미 | 이번에 본 신호 |
|---|---|---|
| `hikaricp_connections_pending` | DB 커넥션을 기다리는 요청 수 | 비관적 락에서 54로 고정 |
| `reactor_netty_connection_provider_pending_connections` | 외부 호출 커넥션 대기 수 | 대출 조회 병목(이번 수정으로 추가) |
| `http_server_requests_seconds` | API별 지연 분포 | k6 p95와 같이 봄 |
| `process_cpu_usage` | CPU 사용률 | 두 병목 모두 CPU는 여유 있었음 |

두 병목 모두 **CPU가 아니라 "기다리는 자원"(행 락, 커넥션 풀)** 이었습니다. 그래서 서버를 늘리는 것(스케일 아웃)으로는 풀리지 않습니다.
- 쿠폰: 락은 DB 행 하나에 있으므로 서버를 늘려도 그대로입니다.
- 대출 조회: 풀 크기가 문제이므로 서버를 늘리면 일부 나아지지만, 대수에 맞춰 풀 크기를 다시 계산해야 합니다.

대기 지표에 알람을 걸고, 대기의 원인(락, 풀, 외부 지연)을 먼저 가르는 순서로 대응합니다.

## 한계

- 앱과 k6가 같은 4 vCPU 러너에 있었습니다. 초당 1,500건 구간은 k6도 자원을 나눠 썼을 수 있습니다.
- 배포 서버(Render 무료, 0.1 CPU)에서는 부하 테스트를 하지 않았습니다. 이 수치는 그 서버의 성능이 아닙니다.
- 모의 금융사는 지연을 흉내 낸 것이고, 실제 기관의 호출 제한이나 네트워크 지연은 없습니다.
